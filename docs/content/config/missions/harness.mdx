# The Harness

The harness is the deterministic authority around a mission's LLM work. A
single mission commander makes bounded orchestration decisions; the harness
decides which decisions are valid and applies them durably.

## Runtime roles

| Role | Responsibility | Tool access |
|---|---|---|
| Mission commander | Coordinate the graph, choose eligible work, inspect results, select declared routes | Intrinsic mission-control operations only |
| Task executor | Complete one bounded task attempt | Exactly the immutable tool grant resolved for that dispatch |
| Harness | Enforce the graph, policy, state machine, identity, budgets, retries, persistence, and validation | Runtime authority; not an LLM |

Managed agents do not participate in mission execution. They are independently
configured assistants whose sessions are started outside missions.

## Why the commander cannot call task tools

The separation is a policy boundary, not a prompt convention:

- Tool credentials and secret bindings are resolved only for the task executor.
- Raw tool results remain in the executor transcript instead of polluting the
  mission commander's context.
- The commander can select only models and optional capabilities declared by
  the mission and task.
- A compromised or confused commander still cannot invoke operational tools.

## What the harness owns

### Ready set and graph transitions

The harness derives the ready set from persisted task state and the declared
graph. Dependencies, concurrency limits, routes, iteration, retries, and paused
human-input events are enforced mechanically.

### Dispatch policy

Before starting a task, the harness resolves and persists its model, tools,
run-as identity, inputs, dependency snapshot, configuration version, and result
contract. A task executor cannot expand that grant after dispatch.

### Results and routing

Every attempt returns a validated result envelope. Optional task output schemas
provide deterministic validation when downstream automation needs typed data.
The commander can select only routes declared by the task; the harness validates
and commits the selection.

### Persistence and resume

Commander decisions, dispatches, transcripts, tool calls, results, routes, and
state transitions are persisted as they occur. Resume reconstructs the mission
commander session and graph state from those records without creating a new
commander for each task.

### Memory and artifacts

Task attempts receive isolated scratch space. Durable artifacts are immutable
and provenance-linked. Persistent mission memory is explicit and its writes are
authorized and serialized by the harness.

## Control flow

1. The harness loads the mission graph and persisted run state.
2. The commander inspects the ready set.
3. The commander requests a task start with an eligible model and optional
   mission-level capabilities.
4. The harness validates and persists an immutable dispatch grant.
5. The task executor reasons, calls its granted tools, and returns a result.
6. The harness validates and persists the result.
7. The commander inspects the result and chooses the next eligible action.
8. The harness completes the mission only when its graph and result rules allow it.
