# Missions

Missions are declarative workflows coordinated by one mission commander. The
harness executes each task in an ephemeral, policy-constrained task executor.

## Basic Structure

```hcl
mission "data_pipeline" {
  commander {
    model     = models.anthropic.claude_sonnet_4
    reasoning = "medium" # optional — see Agents → Reasoning
  }

  models = [models.anthropic.claude_haiku_4_5]
  tools  = [plugins.http.all]

  task "fetch_data" {
    objective = "Fetch the latest data from the API"
    tools     = [mcp.warehouse.query]
  }

  task "process_data" {
    objective  = "Process and analyze the fetched data"
    depends_on = [tasks.fetch_data]
  }

  task "generate_report" {
    objective  = "Generate a summary report"
    depends_on = [tasks.process_data]
  }
}
```

## Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `directive` | string | High-level description of the mission's purpose |
| `commander` | block | The model and context policy for the mission's single commander |
| `models` | list | Models the commander may assign to task executors |
| `tools` | list | Optional capabilities the commander may grant to task executors |
| `input` | block | Mission input parameters (repeatable) |
| `task` | block | Task definitions (repeatable) |
| `dataset` | block | Dataset definitions (optional) |
| `memories` | list | Shared-memory references are not supported by the task-scoped runtime and cannot run. |
| `memory` | block | Mission-scoped persistent memory schema and retention. Tasks opt in with `memory_access`; see [Task Storage](/config/missions/folders). |
| `scratchpad` | bool | If `true`, each task attempt gets an isolated scratchpad slot; the run root is auto-deleted after 7 days. |
| `trigger` | block | Webhook trigger (optional) |
| `max_parallel` | number | Max concurrent instances (default: 3) |

## Mission Inputs

Missions can declare typed inputs that are passed at runtime:

```hcl
mission "report" {
  input "topic" {
    type        = "string"
    description = "The topic to research"
  }

  input "format" {
    type        = "string"
    description = "Output format"
    default     = "markdown"
  }

  task "research" {
    objective = "Research ${inputs.topic} and output in ${inputs.format}"
  }
}
```

| Attribute | Type | Description |
|-----------|------|-------------|
| `type` | string | Input type (`string`, `number`, `integer`, `boolean`, `list`, `map`, `object`, `file`) |
| `description` | string | Human-readable description |
| `default` | any | Default value (makes the input optional) |
| `protected` | bool | Mark the input as sensitive (masked in logs/UI) |

Inputs without a `default` are required. Pass them via CLI:

### Shorthand Schema Syntax

Instead of `input` blocks you can use a single `inputs = { ... }` attribute with schema helper functions:

```hcl
mission "report" {
  inputs = {
    topic   = string("The topic to research")
    format  = string("Output format", { default = "markdown" })
    limit   = number("Max results", { default = 10 })
    api_key = string("API key", { protected = true })
    tags    = list(string, "Tags to apply")
    options = map(string, "Additional key-value options")
    author  = object({
      name  = string("Author name", true)
      email = string("Author email")
    }, "Author information")
  }

  task "research" {
    objective = "Research ${inputs.topic} and output in ${inputs.format}"
  }
}
```

### Protected Inputs

Marking an input as `protected` (via `{ protected = true }` in shorthand or `protected = true` in block form) has the following effects:

- The supplied run value is treated as sensitive and is never written to HCL
- It is **masked in logs and the Squadron app** (displayed as `********`)
- It **cannot be interpolated** in objective strings — authorized task tools receive it through their settings, not through task prompts

```hcl
inputs = {
  api_key = string("Third-party API key", { protected = true })
}
```

```bash
# Supply the protected value when starting the run in Command Center
```

See [Functions](/config/functions) for the complete reference on all helper functions, type references, and the options object (`default`, `protected`).

```bash
squadron mission report -c ./config --input topic="AI safety" --input format=html
```

### File Inputs

A `file` input hands the mission a document to work on. Unlike other inputs,
the contents are **not** interpolated into objectives — instead the file is
exposed to task executors as a **read-only slot** named `input.<name>`, which they read
with the `file_read` / `file_grep` / `file_search` tools, or perceive as an
image, SVG, or PDF with `file_view` (the same tools used for
[memory](/config/missions/folders) and [packets](/config/missions/packets)).

```hcl
mission "analyze" {
  inputs = {
    document = file("The document to analyze", true)
  }

  task "summarize" {
    objective = "Summarize the contents of the document input (slot input.document)"
  }
}
```

File inputs are always required and cannot declare a `default` or be
`protected`. There are two ways to supply the file at run time:

- **Path** — a path inside the project root. Used from the CLI:

  ```bash
  squadron mission analyze -c ./config --input document=./report.md
  ```

- **Base64 upload** — a JSON envelope carrying the filename and content,
  for callers that have no path on the Squadron host (the Squadron product,
  webhooks, and MCP clients calling `run_mission`):

  ```json
  {"filename": "report.md", "content_base64": "IyBSZXBvcnQK..."}
  ```

Either way the file is staged into an isolated per-run slot. Task executors read text
files with `file_read`, and view images (PNG/JPEG/GIF/WebP), SVGs, and PDFs with
`file_view` (SVGs are rasterized to PNG; PDFs are sent as native document
blocks). A single file is capped at 10 MB, and files outside the project root
must be supplied via the base64 form.

## How Missions Execute

1. **Run initialization** - The harness loads the declared graph and creates one mission commander session.
2. **Ready-set calculation** - The harness derives eligible tasks from persisted state and dependencies.
3. **Dispatch** - The commander selects eligible work; the harness resolves and persists an immutable executor grant.
4. **Task execution** - Ephemeral task executors use only their granted models and tools.
5. **Validation and routing** - The harness validates results and route selections before applying graph transitions.
6. **Completion** - The mission finishes only when the graph and result contract permit it.

## Execution Flow

```
┌─────────────────┐
│   fetch_data    │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  process_data   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ generate_report │
└─────────────────┘
```

## Running Missions

```bash
squadron mission data_pipeline -c ./config
```

With inputs:

```bash
squadron mission data_pipeline -c ./config --input source=api --input format=json
```

## Commander Controls

The commander has only intrinsic mission-control operations:

- **inspect_mission** - Read graph state, ready work, budgets, and pending conditions.
- **start_task** - Request an eligible task with an allowed model and capability selection.
- **inspect_task** - Read persisted task progress and results.
- **inspect_mission_memory** - Read declared mission-memory keys on demand when memory is configured.
- **select_route** - Choose one of a task's declared routes.
- **finish_mission** - Request completion when the harness permits it.

See [Internal Controls](/config/missions/internal-tools) for full details.

## Context Protection

When tools return large results (>8KB), Squadron automatically:

1. Stores the full data outside LLM context
2. Returns a sample to the LLM
3. Provides tools (`result_items`, `result_chunk`, etc.) to access more

This prevents context overflow while preserving full data access. Large arrays can be promoted to datasets using `result_to_dataset` for iteration.

See [Datasets](/config/missions/datasets#large-result-handling) for details.

## Structured Outputs

Tasks can define output schemas to capture structured data:

```hcl
task "analyze" {
  objective = "Analyze the data"

  output {
    field "count" {
      type     = "integer"
      required = true
    }
    field "average" {
      type = "number"
    }
  }
}
```

Validated data is included in the dependency context and remains available by
reference for downstream task executors. See [Tasks](/config/missions/tasks#structured-output) for details.

## Persistence & Resume

Mission state is automatically persisted to SQLite during execution. If a mission fails or is interrupted, you can resume it:

```bash
squadron mission data_pipeline -c ./config --resume <mission-id>
```

Resume reconstructs the one commander session, skips completed work, and
reconciles interrupted executor attempts from persisted dispatch state.

See [squadron mission](/config/cli/mission#resume) for details.
