# Tasks

Tasks are the building blocks of missions. Each task has an objective and can depend on other tasks.

## Basic Task

```hcl
task "analyze" {
  objective = "Analyze the data and identify trends"
}
```

## Task with Dependencies

```hcl
task "summarize" {
  objective  = "Summarize the analysis results"
  depends_on = [tasks.analyze]
}
```

## Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `objective` | string | What the task should accomplish |
| `depends_on` | list | Tasks that must complete first |
| `models` | list | Optional subset of the mission model pool that may execute this task |
| `tools` | list | Capabilities always granted to this task's executor |
| `memory_access` | string | Access to declared mission memory: `read` or `read_write`; omitted means none. See [Task Storage](/config/missions/folders). |
| `output` | block | Structured output schema (optional) |
| `router` | block | Conditional routing — LLM picks a branch after task completes (optional) |
| `send_to` | list | Unconditional routing — activate target tasks on completion (optional) |

## Dependencies

Tasks can depend on multiple tasks:

```hcl
task "combine" {
  objective  = "Combine results from both sources"
  depends_on = [tasks.fetch_source_a, tasks.fetch_source_b]
}
```

Dependencies are specified using `tasks.<task_name>`.

## Task Executor Policy

Mission-level `models` and `tools` define pools the commander may assign to
task executors. A task-level `models` list narrows the allowed model pool. A
task-level `tools` list declares capabilities that are always present for that
task, in addition to any optional capabilities selected from the mission pool.

```hcl
mission "pipeline" {
  commander { model = models.anthropic.claude_sonnet_4 }

  models = [models.anthropic.claude_haiku_4_5, models.openai.gpt_5]
  tools  = [plugins.search.all]

  task "draft" {
    objective = "Draft the change description"
    # Either mission model is eligible. Search may be granted at dispatch.
  }

  task "code_review" {
    objective = "Review the code changes"
    models    = [models.openai.gpt_5]
    tools     = [mcp.github.read_pull_request]
  }
}
```

The commander never receives any of these tools. The harness resolves the grant
and supplies it only to the ephemeral task executor.

## Dynamic Objectives

Use variables and inputs in objectives:

```hcl
mission "report" {
  input "topic" {
    type = "string"
  }

  task "research" {
    objective = "Research the topic: ${inputs.topic}"
  }
}
```

## Execution Behavior

The mission commander:

1. Inspects the harness-computed ready set.
2. Requests a ready task with an allowed model and optional mission-level capabilities.
3. Inspects the validated result returned by the task executor.
4. Chooses any declared routing decision and continues coordinating the graph.

## Context from Dependencies

Each task result contains a required status and summary plus optional content,
artifacts, typed data, and diagnostics. The harness persists the result and
supplies a compact dependency snapshot to downstream task executors. Large or
rich results remain available through provenance-linked references.

```hcl
task "step_2" {
  objective  = "Continue based on step 1 results"
  depends_on = [tasks.step_1]
}
```

The executor for `step_2` receives the validated result from `step_1` as dependency context.

## Structured Output

Tasks can define a structured output schema. When defined, the harness validates
the task executor's `data` result against that schema:

```hcl
task "analyze_sales" {
  objective  = "Analyze Q4 sales data"
  depends_on = [tasks.fetch_sales]

  output {
    field "total_revenue" {
      type        = "number"
      description = "Total revenue in USD"
      required    = true
    }
    field "top_product" {
      type        = "string"
      description = "Best-selling product name"
      required    = true
    }
    field "growth_rate" {
      type = "number"
    }
  }
}
```

### Field Types

| Type | Description |
|------|-------------|
| `string` | Text value |
| `number` | Numeric value (float) |
| `integer` | Whole number |
| `boolean` | True/false |
| `list` | Array of values — element type specified via `list(type)` |
| `map` | Key-value pairs — keys are always strings, value type specified via `map(type)` |
| `object` | Structured data with named fields — properties specified via `object({...})` |

### Shorthand Schema Syntax

Instead of `field` blocks you can use a single `output = { ... }` attribute with schema helper functions:

```hcl
task "analyze_sales" {
  objective  = "Analyze Q4 sales data"
  depends_on = [tasks.fetch_sales]

  output = {
    total_revenue = number("Total revenue in USD", true)
    top_product   = string("Best-selling product name", true)
    growth_rate   = number("Growth rate as decimal")
    categories    = list(string, "Product categories found")
    metadata      = map(string, "Additional key-value data")
    breakdown     = object({
      online  = number("Online revenue", true)
      instore = number("In-store revenue", true)
    }, "Revenue breakdown by channel", true)
  }
}
```

Nested types are fully supported — lists can contain objects, objects can contain lists, etc. The task executor receives the full nested schema as its result contract.

See [Functions](/config/functions) for the complete reference on all helper functions and type references.

Structured output is captured, validated, and stored. Downstream executors
receive the relevant data in their dependency context or by reference.

## Routing

Tasks can route to other tasks (or missions) after they complete. See [Routing](/config/missions/routing) for full details, including [when to use `depends_on` vs `router` vs `send_to`](/config/missions/routing#choosing-between-depends_on-router-and-send_to).

> **Rule of thumb:** prefer `depends_on` and build a static DAG. Reach for `router` only when the LLM must choose a branch, and `send_to` only for fan-out or conditional fan-in to a shared task.

### Conditional Routing

A `router` block lets the LLM choose which branch to activate:

```hcl
task "classify" {
  objective = "Classify the request"
  router {
    route {
      target    = tasks.handle_billing
      condition = "The request is about billing"
    }
    route {
      target    = tasks.handle_support
      condition = "The request is technical support"
    }
  }
}
```

### Unconditional Routing

`send_to` activates target tasks immediately — no LLM decision:

```hcl
task "fetch" {
  objective = "Fetch data"
  send_to   = [tasks.process_a, tasks.process_b]
}
```

> **Note:** `router` and `send_to` are mutually exclusive on a task. Dynamic targets (tasks reachable via `router` or `send_to`) cannot have `depends_on`.
