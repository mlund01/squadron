# Iteration

An iterated task applies the same task policy to each item in a mission dataset. Squadron has one commander for the mission run. The harness freezes the dataset into numbered child task instances when the parent task becomes ready; it never creates a commander per item.

```hcl
task "get_weather" {
  objective  = "Get the current weather for the supplied city"
  depends_on = [tasks.load_cities]
  models     = [models.fast]
  tools      = [builtins.http.get]

  iterator {
    dataset           = datasets.city_list
    parallel          = true
    concurrency_limit = 5
    smoketest         = true
    max_retries       = 2
  }
}
```

Each child receives its own item and index in the task-worker prompt. For example, `get_weather[2]` receives item 2 from the frozen dataset. The commander sees child task names and bounded result summaries, chooses an allowed model and any relevant mission-level tools, and can inspect a child's accepted output when needed. The task's declared tools are always granted to its children. The commander cannot call those tools directly.

The dataset is locked before expansion. Its ordered items and digest are persisted with the mission checkpoint, so restarting a run does not reread a changed dataset or generate different child identities. A dataset may be populated by an earlier task using a declared `builtins.dataset.set` capability.

## Scheduling

By default, children run sequentially: `task[1]` becomes eligible only after `task[0]` succeeds. With `parallel = true`, independent children can run concurrently, bounded by both the iterator's `concurrency_limit` (default 5) and the mission's maximum parallelism. `smoketest = true` makes every later child wait until child 0 succeeds. Each child has its own attempts and `max_retries` policy.

`start_delay` sets the milliseconds between worker starts in the first parallel batch. The harness persists each child's earliest start time with its dispatch, so a restart preserves the stagger without rerunning an attempt. It does not replace a downstream service's own rate limit.

An empty dataset completes the parent task without launching a worker. Once every child succeeds, the parent completes and downstream dependencies become eligible. If an attempt exhausts its retries, the mission fails rather than treating a partial set of children as a successful parent.

## Results

If the task declares an output schema, the harness validates each child against that schema before accepting it. Child outputs, artifacts, transcripts, and telemetry remain separately attributable.

After every child succeeds, the parent receives an ordered aggregate of accepted child results. Each entry identifies its child index and task name and includes its summary, structured data, and artifact references. The aggregate is a projection, not a newly generated model answer or a merge of the children's output schemas. A downstream task receives it as the accepted result of its declared parent dependency. The commander can still inspect an individual child for its full accepted result.

The model-visible aggregate is bounded to 1 MiB. If child data and artifact references do not fit, that entry retains a shortened summary and marks `detailsOmitted`; if even those entries cannot fit, `omittedItems` reports how many tail entries were omitted. The full child results remain persisted and independently inspectable. Never treat an incomplete aggregate as the complete dataset.
