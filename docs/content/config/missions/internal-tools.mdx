# Internal Controls

The mission commander receives a small intrinsic control surface. These
operations are implemented by the harness and are not plugin, MCP, or built-in
tools. They cannot expose task credentials or invoke task capabilities.

## `inspect_mission`

Returns the current mission status, declared graph, ready set, running work,
completed results, pending human input, and remaining budgets.

## `start_task`

Requests execution of a ready task. The request identifies the task, selects an
allowed model, and may select capabilities from the mission-level pool. The
harness rejects tasks outside the ready set and any model or capability outside
the declared policy.

Task-level tools are always included in the resulting immutable grant.

## `inspect_task`

Reads the accepted result for a completed task in bounded JSON byte chunks.
The commander starts at `offset = 0` and follows `nextOffset` when it needs
more. The full executor transcript and raw tool activity are excluded from
this control and remain available to operators through run drill-in.

## `inspect_mission_memory`

Available when the mission declares persistent memory. Reads one declared,
non-secret key in bounded JSON byte chunks; it does not mutate memory. The
first page returns a version and `next_offset` when more data remains. Later
pages pass that version as `expected_version`; a stale response means the key
changed and the commander should restart at offset zero. Each read result is
durably recorded with the commander turn so recovery replays the same value.

## `select_route`

Selects one of the routes declared by a completed routing task. The harness
validates the selection and applies the graph transition atomically.

For a cross-mission route, the commander supplies `inputs` from the
destination's visible input contract. Values may use native JSON types or
string-encoded values. Optional values may be omitted to use their defaults;
explicit `null`, unknown names, and values that do not match the destination
type are rejected together. Protected inputs are never exposed to the
commander and retain their configured values.

## `finish_mission`

Requests mission completion. The harness accepts the request only when required
work is complete and no unresolved runtime condition prevents completion.

## Task executor tools

Task executors receive only the capabilities in their persisted dispatch grant:

- tools declared directly on the task; and
- optional tools selected from the mission-level pool.

The commander never receives these tools. Dataset access, result paging, file
access, human-input requests, MCP tools, plugin tools, and built-ins follow the
same grant rule rather than being implicitly added to the commander.
