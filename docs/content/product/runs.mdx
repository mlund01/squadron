# Running Missions

Open a mission and select **Run mission**. Squadron checks authorization before showing the run form or sending work to the connected worker.

## Choose an execution identity

The run dialog always appears, even when the mission has no configured inputs. It shows the identities that may execute this mission:

- **Yourself**, when your workspace role and mission grants allow it.
- **A service principal**, when you may use it and it has a Run grant for the mission.

When multiple identities are available, choose one before starting the run. Squadron defaults to your user identity when it is eligible; otherwise it selects the first eligible service principal by name.

## Provide inputs

Mission input fields come from the mission's HCL definition. Protected values are handled as inputs rather than rendered into configuration. File inputs are uploaded as structured content and materialized read-only by the worker.

## Follow execution

The run page is organized from high-level context to deeper telemetry:

1. Mission inputs and run state
2. The execution canvas
3. The task execution timeline
4. Aggregate model, tool, time, and cost telemetry when available

One commander session coordinates the whole run. **Commander conversation** opens
that session; selecting a task on the canvas or timeline opens its separate task
executor session. A task executor is mission-owned work, not a managed agent.
Its drill-in includes the task objective, granted model and tools, persisted
conversation, accepted result, and any attempts or retry state.

The execution timeline uses a shared mission clock: overlapping task bars
represent parallel work, while multiple bars on one task represent retries.
For an iterated task, the canvas card reports how many child executions have
finished. Open that card to choose a specific child session; the timeline shows
one row per child execution rather than counting the iteration parent as work.
The floating session panel has **Chat** and **Trace** tabs and can expand while
keeping the selected session and tab. Chat renders commander decisions and task
tool calls from the persisted transcript; tool inputs, results, and attachments
remain inside their expandable call. Trace shows persisted state transitions and
attempt details. A waiting task displays its human-input request or retry
deadline so the operator can distinguish waiting from active work.
When a route launches another mission, the parent run links directly to the
separately recorded child run. The child has its own commander, inputs, identity,
and execution timeline.

Only actual runtime records appear in these views. A newly started run may show
ready tasks before its first commander turn has finished. While a commander or
executor is active, Chat shows a working indicator even before its next full
turn is checkpointed; the transcript updates as persisted work becomes
available. Trace continues to show persisted events rather than provisional
activity.

## Stop and resume

Runs may be stopped and resumed when the current identity is allowed to control them. The initiating user retains control of a run started as a service principal. Managers and Admins can control any run in their workspace.

## Disconnected workspaces

A mission cannot start while its workspace worker is disconnected. The workspace status indicator and run controls surface this state without discarding the mission definition or prior run history.
